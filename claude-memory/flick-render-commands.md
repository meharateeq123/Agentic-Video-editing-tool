From inside a flick project's `remotion/` folder on this machine (Node 24, Windows PowerShell — no `&&`, use `;`):

- Studio: `npx remotion studio src/index.tsx --port 3011` (background; prints "Server ready" after ~25s). Kill it before a long render — the box is a 6-core Xeon W3680 with only 8 GB RAM, and Studio's Chrome competes directly with the render workers.
- QC still: `npx remotion still src/index.tsx final-film ../qc/<name>.jpg --frame=<n> --image-format=jpeg`
- 4K comes from `--scale=2` on the 1920x1080 composition, not from resizing the composition.
- This box has a GTX 1650 (4GB VRAM). `--gl=angle` makes Remotion's headless Chrome use it for frame compositing (the actual per-frame bottleneck — filters like the bed blur). That is a separate thing from FFmpeg's hardware *encoding* path (`--hardware-acceleration=if-possible`): that flag conflicts with `--crf` ("crf option is not supported with hardware acceleration") and killed a render silently. Use `--gl=angle` alone; do not add `--hardware-acceleration`. **The user wants `--gl=angle` (GPU) used, confirmed explicitly on larson1 after a mid-render mix-up where it got swapped to `--gl=swiftshader` (CPU) — swap back immediately if this ever happens again, don't guess.**
- **This box's real render bottleneck is RAM, not GPU.** Only 8GB total, and the user routinely runs 20-30 Chrome browser tabs alongside (3-4GB). When free RAM drops below ~1.5GB, `npx remotion render` can hang indefinitely at startup with zero output — no error, no worker process, nothing in the log — and just sit there. There's no fixed process to "clean up": check `Get-CimInstance Win32_OperatingSystem` free memory before assuming a render is broken, and ask the user to close some Chrome tabs (don't close their browser windows yourself) if it's under ~2GB. 3GB+ free was enough for larson1's chunks to start normally.
- Never `taskkill /IM chrome.exe /F` to clean up a dead Remotion render — that also kills the user's real desktop Chrome (same binary name). Remotion's render workers show no matching process once the render driver itself has exited; check for a live `node.exe`/render script process first, and if headless workers are still running, filter by command line (`remotion`/`headless-shell`), never by bare image name.

**Always render from a pre-built bundle, never from `src/index.tsx`.** Rendering from source makes Remotion re-bundle and copy the whole `public/` dir (2.6GB of bed-pool footage on bell1) into a fresh temp folder on *every* invocation. On this box that copy is where renders die silently — no error in stdout or stderr, process simply gone, four times in one session, leaving 55 orphaned `%TEMP%\react-motion-render*` / `remotion-v*-assets*` dirs behind. Instead:
- once: `npx remotion bundle src/index.tsx --out-dir=<proj>\bundle` (~2 min), and re-run it after any `src` change;
- per chunk: `npx remotion render <proj>\bundle final-film <out> --frames=<s>-<e> ...` — run from inside `remotion/` so `npx` resolves, but pass the bundle path absolutely.
After this change all 7 chunks rendered without a single failure at ~11 min per 1500 frames (~2.3 fps at 1080p). Also add `--timeout=180000`: OffthreadVideo's first seek into a 0.5-1.2GB bed blows past the 28s default and fails the render at frame 0. Sweep `%TEMP%` for those orphan dirs when disk gets tight. **Do this sweep BEFORE every long render, not after a failure:** on yuzidi1 (2026-09-13) 153 stale `remotion-v*-assets*`/`react-motion-render*`/`remotion-webpack-bundle-*` dirs held 44.8GB, C: was down to 6.8GB, and part08 failed at the stitch step with `Error opening output ...remotion-stitch-temp-dir\fast-start-intermediate.remotion-in-progress: No such file or directory` (Windows removed temp contents under disk pressure). Delete only dirs with LastWriteTime older than the running chunk's start. The same box also hard-rebooted 3 times that day (event 41, unclean shutdown) — a scheduled task (`schtasks /Create /SC ONCE` + `/Run`) survives session teardown but NOT a reboot; re-run it after one and the chunk skip logic resumes.

**Don't re-encode whole long sources into bed-pool.** On phelps1 (2026-09-14) three parallel full-file libx264 transcodes (1h keynote, 32min Olympic compilation, etc.) crawled for 12+ min with RAM down to 0.85GB and produced almost nothing. Downloads are already h264 (the yt-dlp format string asks for avc1), so hardlink them into `public\bed-pool` (`New-Item -ItemType HardLink`) and only transcode the few files that need a baked crop (watermark/bug/lower bar), one at a time with `-threads 4`. Also: background PowerShell loops don't carry `phelps1` in their own command line, so killing ffmpeg by command line only advances the loop to its next file — stop the task itself (TaskStop) first.

**Never run a full-film render inside a Claude background shell.** A 4K pass here is ~2s/frame — nearly 6 hours for a 5-minute film — and one such render died at frame 3022 of 9930 with no output when the Claude Code process exited. Instead use the pattern in `output/reddick1/render-4k.ps1`:
- render in 1500-frame chunks (`--frames=<s>-<e>`) into a `parts4k/` folder, writing each to a `.tmp.mp4` and renaming on success, so re-running the script resumes rather than restarting;
- render chunks `--muted` and mux the single full-length VO wav on at the end with ffmpeg (`ffmpeg-static`, resolved via `node -e "require('ffmpeg-static')"`), so audio never crosses a chunk seam;
- **launch it with `Invoke-CimMethod -ClassName Win32_Process -MethodName Create -Arguments @{CommandLine = 'cmd.exe /c powershell -NoProfile -ExecutionPolicy Bypass -File <script> >> <log> 2>&1'}`.** `Start-Process ... -WindowStyle Hidden -RedirectStandardOutput <log> -PassThru` is NOT enough: on larson1 a render launched that way died silently mid-chunk when the session was re-initialised by a `/model` switch, because the spawned process was still inside the shell's process tree. `Win32_Process.Create` spawns a genuinely unparented process that survives session teardown. Poll the log for progress either way.
- Give each chunk **its own retry loop (3 tries)** inside the script rather than `exit 1` on first failure — a retry costs ~11 minutes, a stalled overnight run costs the whole render. Step concurrency down across the retries (`foreach ($conc in @(2,1,1))`), since two workers double the memory pressure.
- **Always pass `--offthreadvideo-cache-size-in-bytes=134217728`.** Uncapped, OffthreadVideo's frame cache starves this 8GB box and Remotion's own proxy server starts answering **500 Internal Server Error** on `/proxy?src=...&time=...` requests, killing the chunk. On larson1 this killed part04 twice at `final-laps.mp4` t=119.4s — and the giveaway that it is *not* bad source data is that `ffmpeg -ss <t> -i <file> -frames:v 1 -f null -` decodes that exact timestamp cleanly. Scenes that seek repeatedly into one large bed file (larson1's scene 12 hits `final-laps.mp4` at 116/123/20/30s) are the ones that trigger it.

**Joining the chunks — two ffmpeg traps, both of which fail while still exiting 0:**
- **Video:** `-f concat -safe 0 -i list.txt -c copy` runs `h264_mp4toannexb` over Remotion's MP4 chunks, that filter chokes (`Invalid NAL unit size (0 > N)`) and ffmpeg stops partway through part01 — on larson1 it turned 325s of rendered parts into a 19-second file and still returned exit 0. **Add `-auto_convert 0`.** Converting the parts to MPEG-TS first does *not* work here either; the same bitstream filter fails on the conversion.
- **Audio:** the concat demuxer over two raw `.aac` files silently keeps only the first input (larson1 ended up with a 16s hook-only track). Build the track with the concat **filter** in one re-encode instead: `-t <hook secs> -i hook.mp4 -i vo.wav -filter_complex "[0:a]aresample=48000,aformat=sample_fmts=fltp:channel_layouts=stereo[a0];[1:a]...[a1];[a0][a1]concat=n=2:v=0:a=1[out]" -map "[out]" -c:a aac -b:a 192k`. Trim the hook to exactly `HOOK_FRAMES / FPS` (e.g. 16.0s, not the clip's own 16.003s) so the VO starts on the frame scene 1 mounts on.
- **Always verify the joined duration with ffprobe** rather than trusting exit codes.

**A chunk can "succeed" and still be broken — always run freeze detection on the finished film:**
`ffmpeg -hide_banner -i final-film.mp4 -vf "freezedetect=n=-60dB:d=2" -map 0:v:0 -f null - 2>&1 | Select-String 'freeze'`
When the OffthreadVideo proxy starts failing, Remotion does not always error out — sometimes it just keeps painting the last decoded frame, so the chunk finishes, exits 0, and looks the right size while containing a long freeze. On larson1 part01 (rendered at concurrency 2 with no cache cap, before those were fixed) this produced a **30.8-second frozen shot** that no exit code or file-size check would have caught; the user spotted it on playback. The freeze ending exactly on a chunk boundary is the tell for which part to re-render — delete just that `partNN.mp4` and re-run the script, which resumes and rebuilds only it.

**Why:** Long renders on this hardware outlast the session that starts them, and an unchunked render loses hours of work to any interruption.

**How to apply:** Poll the log rather than blocking; check the VO duration matches the composition length before committing hours to a render. Related: [[reddick-southern-500-film]].

**Raw-footage crop/transcode (ffmpeg, not the Remotion render) cannot use the GPU on this box.** Two separate hard blocks, confirmed 2026-09-08:
- `h264_nvenc` fails outright: "Driver does not support the required nvenc API version. Required: 12.1 Found: 11.1" — installed driver is 472.47, this ffmpeg-static build needs ~530+. A driver update might fix encode, but is a system-level change to confirm with the user first, not something to do mid-task.
- Most yt-dlp downloads for these NASCAR films land as **AV1** (confirm per-file with `ffprobe -show_entries stream=codec_name`). The GTX 1650 is Turing (TU117), which has **no AV1 decode hardware at all** — this is a fixed hardware limit, unrelated to driver version, and cannot be worked around. So even fixing NVENC wouldn't help AV1 sources, since decode (not encode) is the actual bottleneck and stays on CPU regardless.
- **How to apply:** Don't retry `h264_nvenc` or `-hwaccel` flags on this machine's raw-footage prep step — go straight to CPU `libx264`, and use multiple parallel PowerShell workers (one ffmpeg process per source) to get real throughput instead. This is separate from `--gl=angle`, which *does* work — that's Chrome's GPU compositing during the Remotion render itself, not ffmpeg's encoder.
- **Root cause, traced 2026-09-08 on the bell1 project:** the yt-dlp format string used for downloads was `-f 'bv*[height<=1080][ext=mp4]/bv*[height<=1080]'` — it constrains resolution and container but not codec, so YouTube's "best" stream under 1080p was AV1 for 5 of 7 sources, and nothing caught it until a contact-sheet scan ran slow. **Fix at the download step, not after**: add a codec filter so AV1/VP9 is never fetched in the first place — `-f 'bv*[height<=1080][vcodec^=avc1]/bv*[height<=1080]'`. Confirm per-file after download with `ffprobe -select_streams v:0 -show_entries stream=codec_name -of csv=p=0 <file>` before kicking off a crop/transcode pass on this box.
